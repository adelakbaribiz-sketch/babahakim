## 1. قراردادها

- **شناسه صفحه:** `SC-{AREA}-{NN}` — پایدار؛ در Issue/تست/Trace فاز UI rebuild استفاده می‌شود (ED-71).
- **۹ فیلد اجباری هر صفحه:** هدف · کاربر · اطلاعات · Actions · دسترسی · Empty · Loading · Error · Success (فرمان PHASE 06).
- **الگوهای حالت (SP):** از `UX.md` §۷ — SP-1/2 (Loading کارت/جدول) · SP-3/4 (Empty لیست/First-run) · SP-5/6 (Error Fetch/Action) · SP-7/8 (Success Action/جریان). هر صفحه الگو + محتوای اختصاصی می‌گوید (ED-74).
- **دسترسی:** برای staff = Permission از کاتالوگ ۳۱تایی (`src/lib/constants.ts`)؛ «+Session نقش» یعنی شرط نقش علاوه بر Permission؛ برای PATIENT = مدل **مالکیت** (ED-77) — سرور داده‌ی غیرمالک را نمی‌دهد.
- **وضعیت Case:** نام وضعیت‌ها = ۲۱ وضعیت رسمی (`WORKFLOW.md`)؛ اکشن‌ها = ۱۹ اکشن ماشین CASE.
- **Route v2:** مسیر RESTful هدف (مهاجرت طبق ED-79)؛ در v1 همه صفحات داخل SPA با view-state رندر می‌شوند.

## 12. مدل دسترسی و یادداشت امنیتی

1. **UI منبع مجاز نیست (UX-07/ED-77).** هر چیزی که این سند «دسترسی» نامیده، الزامِ رندر است؛ اجرای واقعی همیشه در سرور (Permission/مالکیت/وضعیت ماشین) است. مخفی‌سازی دکمه کنترل امنیتی نیست.
2. **PATIENT مالکیت‌محور است**: کاتالوگ Permission برای PATIENT خالی است (`ROLE_PERMISSIONS.PATIENT = []`) — دسترسی بیمار از رابطه مالکیت (Case.patientId = خودش و …) در سرور اثبات می‌شود. صفحه‌های PT هرگز Permission نام نمی‌برند.
3. **اکشن‌های حساس همیشه دومرحله‌ای** رندر می‌شوند: Confirm-با-ورودی برای تخریب‌پذیرها (ANONYMIZE/DEPLOY/تغییر نقش ADMIN) و AlertDialog برای گیت‌های چرخه (G1/G3/تصمیم پزشک).
4. **داده‌ی تصویر/پرونده** فقط از طریق Signed-URL موقت نمایش داده می‌شود (ED-66: VIEW_MEDICAL_FILE برای staff؛ PATIENT = مالکیت)؛ PHILE در UI هرگز ثبت نمی‌شود — ردیابی‌ها به «Audit ثبت شد» بسنده می‌کنند.
